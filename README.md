# Mobil
### An implementation of the calculus from my thesis: *Coeffects for Code Mobility*. 

[Code mobility](https://en.wikipedia.org/wiki/Code_mobility) refers to the marshaling of *code* rather than *data* &mdash; a concept that has been in circulation for decades with the initial hope that it would find use in [mobile agents](https://en.wikipedia.org/wiki/Mobile_agent) but eventually failed for that purpose due to complexity and security concerns. Ultimately, coarse-grained code mobility became ubiquitous in the WWW in many forms (e.g. JavaScript, WASM, Edge-computing), "coarse-grained" meaning that code is packaged and transferred in entire, standalone (sandboxed) modules/programs rather than in bits and pieces. Fine-grained code mobility has seen prominence in data science and analytics. Engines like [Apache Spark](https://spark.apache.org/) allow programmers to execute custom code on distributed worker nodes that are more performant and closer to the data. Code mobility has certainly found its place in various industry-wide settings. But its accompanying problem of requirements tracking is often glossed-over. 

It's not always feasible to transfer the entire runtime environment marshaled code requires to execute (e.g. Docker Images). This can be due to the environment being too large, impractical to send, or containing confidential information. This means that certain resources must be provided by a receiving end before the code can be executed. The aforementioned instances of code mobility often lack flexibility in the approaches to this: WASM modules, being coarse-grained, impose whole-program requirements even if only part of the program will be executing; code for Spark is written in languages that lack sufficient static analyses for detecting implicit resource captures in lambdas, leading to the dreaded (runtime) `NotSerializableException`. The Mobil language developed in my thesis work proposes an alternative choice for modeling code mobility using a recent innovation in type systems research: coeffects.

Coeffects grade modal types and type-contexts with an algebraic structure (e.g. semiring) tracking requirements for terms &mdash; seemingly a natural fit for the problem of code mobility but has surprisingly seen limited investigation. The Mobil language is an simply-typed lambda calculus extended with coeffect-graded modal types (inspired from modal logic) that demonstrates what a type system like this might look like and what it might be capable of. The language type system can track the requirements a term needs to execute throughout its marshaling and sending process and ensure at compile time that a receiving end can provide those requirements (avoiding the `NotSerializableException`); it can also provide a runtime framework or enforcement for graceful handling when static checks are not possible; additionally, it can provide the ability for a receiver to sandbox the resources it provides. These are all features that can be offered as first class by Mobil.
